# 代码实验：多线程下 `STATS["ok"] += 1` 会不会丢计数

> 日期：2026-10-17　来源：审查 [review-demo/sample_service.py](<../../review-demo/sample_service.py>) 时提出的疑问
> 假设：`dict` 元素的 `+= 1` 不是原子操作，多线程并发时会丢计数。

## 一、实验设计

| 项 | 设定 |
|---|---|
| 变量 | 是否用锁保护计数 |
| 固定条件 | 8 个 worker，每个累加 10000 次，合计期望 80000 |
| 观测 | 最终计数值 |
| 判定 | 无锁组 < 80000 即假设成立；加锁组应恒等于 80000 |

## 二、实验脚本

```python
import threading
from concurrent.futures import ThreadPoolExecutor

STATS = {"ok": 0}
LOCK = threading.Lock()


def bump_unsafe(n):
    for _ in range(n):
        STATS["ok"] = STATS["ok"] + 1      # 读 → 改 → 写，三步之间可能被打断


def bump_locked(n):
    for _ in range(n):
        with LOCK:
            STATS["ok"] += 1


def run(fn, workers=8, per=10_000):
    STATS["ok"] = 0
    with ThreadPoolExecutor(max_workers=workers) as pool:
        list(pool.map(lambda _: fn(per), range(workers)))
    return STATS["ok"]


if __name__ == "__main__":
    expect = 8 * 10_000
    print(f"{'无锁':<6} 实测={run(bump_unsafe):<7} 期望={expect}")
    print(f"{'加锁':<6} 实测={run(bump_locked):<7} 期望={expect}")
```

## 四、结论与修复

- **结论**：`STATS["ok"] = STATS["ok"] + 1` 对应"读-改-写"三步，线程切换点落在中间就会互相覆盖 → 丢计数。
- **修复**：① 用 `threading.Lock` 包住；② 或用 `concurrent.futures` 的返回值在主线程汇总（无共享状态，最省心）。
- **反例提醒**：把计数换成"往 `dict` 里写不同 key"（`CACHE[user_id] = data`）时，CPython 内部不会崩，但同一次任务的多字段仍可能读到半更新状态——所以锁保护的范围应覆盖"整组相关写入"，而不只是单个赋值。

## 五、可迁移的判据

> 只要满足"多个线程 + 共享可变状态 + 非单条 C 层指令完成"，就要怀疑原子性。
> 判断方式不靠记忆：**写个 20 行脚本实测一次**，比争论"GIL 会不会保护你"快得多。
